## 1. Executive Summary

A comprehensive read-only security audit was conducted on the Traditional Billing setup-token lifecycle. The system governs initial company and administrator onboarding via a one-time cryptographic bootstrap authorization mechanism.

- **Cryptographic Strength**: **High** (192-bit entropy via `secrets.token_hex(24)`).
- **Transport Security**: **High** (Native Qt desktop password dialog; token is never passed through or accessible to browser JavaScript/QWebEngine).
- **Verification Integrity**: **High** (Constant-time comparison via `secrets.compare_digest`, single-use post-commit file shredding, permanent database-level lockout).
- **Identified Weaknesses**:
  1. The token file on disk stores the token as plaintext rather than a one-way cryptographic hash (SHA-256).
  2. There is no time-based expiration (TTL) on an unconsumed token file.
  3. The provisioning script lacks an explicit `APP_ENV` safety check to warn operators if targeting a remote database.

**Final Verdict**: **SAFE WITH CONDITIONS**.

## 3. Detailed Audit Findings Against Specification

### 1. How the Token is Generated
- **Mechanism**: Generated by `provision_setup_token()` in `services/traditional_setup_token.py`.
- **Implementation**: Uses Python's standard library `secrets.token_hex(24)`.
- **Entropy Source**: Connects directly to the host operating system's cryptographic CSPRNG (`os.urandom` on POSIX/macOS, `CryptGenRandom` / `BCryptGenRandom` on Windows).
- **Output**: A 48-character hexadecimal string representing 24 cryptographically random bytes ($24 \times 8 = 192$ bits of entropy).

### 2. Cryptographic Security and Uniqueness
- **Entropy & Collision Probability**: With 192 bits of entropy ($2^{192} \approx 6.27 \times 10^{57}$ states), the probability of collision or brute-force guessing is mathematically zero under current computing capabilities.
- **Overwrite Protection**:
  - Running `provision_traditional_setup_token.py` when a token file already exists refuses to overwrite it (preserving the existing token).
  - An operator must explicitly specify `--force` to rotate and regenerate the token.
  - The file is created using atomic POSIX flags `os.O_WRONLY | os.O_CREAT | os.O_EXCL`, preventing race conditions.

### 3. Location of Stored Token
- **Canonical Path**: `config.DATA_DIR / ".traditional_setup_token"`.
- **Path Resolution**: Absolute path dynamically resolved by `get_canonical_setup_token_path()`.
- **Filesystem Permissions**: Strictly enforced as `0600` (`-rw-------`, Owner Read/Write only) using `os.open()` and `os.chmod()`.
- **Source Control Safety**: Explicitly excluded from Git tracking in `.gitignore` under `.*setup_token*`.

### 4. Storage Subsystem Classification
- **Local SQLite**: **NO** (Not stored in SQLite).
- **Remote PostgreSQL**: **NO** (Not stored in PostgreSQL).
- **Environment Variables**: **NO** (Not stored in `.env` or environment variables).
- **Actual Location**: Stored exclusively as an **isolated flat file on the local filesystem** (`.traditional_setup_token`).

### 5. Database Configuration Used
- The provisioning script instantiates `TraditionalCompanyService(traditional_db_manager)`.
- `traditional_db_manager` reads `TRADITIONAL_DATABASE_URL` (or falls back to `config.get_traditional_database_path()`, resolving to `traditional_billing.db` or `staging_traditional_billing.db` based on `APP_ENV`).
- **Database Interaction Scope**: Strictly read-only (`SELECT count(id) FROM companies`). The provisioning script executes zero `INSERT`, `UPDATE`, or `DELETE` statements against the database.

### 6. Independence Across Multiple Machines Sharing Identical `.env` Files
- **Status**: **100% Independent**.
- Tokens are generated locally using the host machine's hardware entropy pool (`os.urandom`).
- No `.env` parameters, seeds, or static secrets are used during generation.
- The resulting file resides solely on that machine's local disk. Two machines with byte-for-byte identical `.env` files will generate completely different, uncorrelated tokens.

### 7. Cross-Computer Token Reusability
- **Status**: **Cannot be reused across computers**.
- Verification occurs on the desktop host where `BackendBridge.traditional_initialSetup()` is running.
- It verifies the entered token strictly against the local token file (`token_path.read_text()`).
- If Computer B lacks a locally provisioned token file, `token_path.exists()` evaluates to `False`, failing closed with:
  `"Bootstrap setup token file not found. Please run 'python scripts/provision_traditional_setup_token.py' to provision."`
- Entering Computer A's token into Computer B fails constant-time comparison unless someone physically copies the `.traditional_setup_token` file out-of-band onto Computer B's filesystem.

### 8. Single-Use, Expiration, and Revocation
- **Single-Use**: **YES (Enforced)**.
  - Upon successful database commit of the initial company and administrator, `consume_setup_token()` is invoked.
  - The token file is overwritten with 48 zeroes (`"0" * 48`) to shred disk remnants and immediately unlinked via `unlink()`.
  - Once committed, `Company.count() >= 1`. The service write lock raises `PermissionError("Initial setup is permanently closed")` on any future attempt.
- **Expiration (TTL)**: **NO**.
  - There is currently no time-based expiration (e.g., 15 or 30 minutes). If generated but unconsumed, the token file remains valid until consumed, rotated, or deleted.
- **Revocation**: **YES**.
  - Can be rotated/revoked by running `python scripts/provision_traditional_setup_token.py --force`.
  - Can be revoked by deleting `.traditional_setup_token`.
  - If a company is created through any other channel, subsequent runs automatically delete the token file.

### 9. Storage Security: Plaintext vs Hash
- **Status**: **Stored as PLAINTEXT on disk**.
- **Audit Finding**: In `services/traditional_setup_token.py` line 77, `f.write(token + "\n")` writes the plaintext token directly into `.traditional_setup_token`.
- **Risk Assessment**: While mitigated by POSIX `0600` permissions, hidden file naming, `.gitignore` exclusion, and single-use post-commit deletion, plaintext storage violates the principle of defense-in-depth. Any process running under the same OS user account could inspect the file before setup is completed.

### 10. Risk of Accidental Targeting of Production
- **Existing Production Installation**: **Zero Risk**.
  - If production already has one or more registered companies (`count > 0`), the script immediately exits with an error without writing a token.
- **Fresh / Uninitialized Production Database**: **Low to Moderate Risk**.
  - The script lacks an explicit check for `APP_ENV=production` or interactive confirmation if connected to a remote PostgreSQL URL.
  - If a developer's local environment inadvertently points `TRADITIONAL_DATABASE_URL` to an uninitialized remote production database, running the script writes a token locally on the developer's laptop. The developer could then execute initial setup against that database.
  - However, because the script performs only a read-only `count()` check, it cannot corrupt or alter existing data.

## 4. UI & Transport Boundary Audit

* **Frontend Protection**: `app.js` (`window.backend.traditional_initialSetup`) packages only company metadata and administrator credentials. The token is never exposed to, handled by, or routed through the WebEngine browser runtime.
* **Native Dialog**: When `traditional_initialSetup` is triggered in the desktop app, `BackendBridge` displays a native `QInputDialog` with `QLineEdit.Password` masking on the desktop OS layer.
* **Comparison**: The comparison is executed in Python using `secrets.compare_digest()`, completely preventing timing side-channel attacks.

---

## 5. Required Conditions & Hardening Recommendations

To advance from `SAFE WITH CONDITIONS` to unconditional `SAFE`:

1. **Hash Storage on Disk (Defense-in-Depth)**:
   - In `provision_setup_token()`, store `hashlib.sha256(token.encode('utf-8')).hexdigest()` in `.traditional_setup_token`.
   - In `verify_setup_token()`, hash the entered token and compare:
     `secrets.compare_digest(hashlib.sha256(entered_token.encode('utf-8')).hexdigest(), stored_hash)`.
   - This ensures that even if the file is read, the plaintext bootstrap token cannot be obtained.
2. **Time-To-Live (TTL) Expiration**:
   - Store creation timestamp alongside the hash in JSON format: `{"hash": "...", "created_at": 1731999999}`.
   - Enforce a 30-minute expiration window in `verify_setup_token()`.
3. **Environment Warning in Provisioning CLI**:
   - If `traditional_db_manager.is_postgres` is True or `config.is_production()` is True, display a prominent confirmation prompt before writing the local token file.

---

## 6. Audit Verdict

### **SAFE WITH CONDITIONS**

The Traditional Billing setup token mechanism provides strong cryptographic protection (192-bit CSPRNG, constant-time compare, native Qt modal isolation from WebEngine JS, atomic single-use shredding, and permanent DB lockout). It is safe for operation provided operators are aware that the unconsumed token file is stored as owner-readable (`0600`) plaintext without a time-based TTL.
